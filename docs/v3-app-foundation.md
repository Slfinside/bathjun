## 製品構成

| 製品 | 役割と条件 |
| --- | --- |
| 従来のWindowsサーバー | 継続利用可能。既存の予約・抽選・認証・報告・スタンプ・アイテム等のルールと保存データを保護する |
| bathjun Server | iOS・Android向け買い切り有料の管理用アプリを想定。家庭の初期セットアップ、メンバー、ルール、ダッシュボード等を扱う。家族の利用・予約確定に管理アプリの常時起動を要求しない |
| ふろじゅん | 無料のiOS・Androidクライアント。どちらの構成にも「QRコードを読み取って参加」で接続する。通信方式の差はアプリ側で吸収する。Windows利用家庭に管理アプリ購入を要求しない |

広告を入れず、運営側の継続費用を小さくする。iPhoneだけの家庭も対象。価格は通常1,500円前後・公開初期1,000円前後という仮案で、実測費用を基に確定する。年額課金の合意はない。iOS購入をAndroidで利用する権利の証明・復元は未設計で、自動共有できると扱わない。今回、ストア公開・課金設定・クラウド契約は実施しない。

## 段階と技術選定

1. 共通ID、通信仕様、移行形式とUIを整える（今回）。
2. 既存WindowsサーバーにつながるiOS・Android版ふろじゅんを実装する。
3. bathjun Server、新しい同期方式、Windowsとの双方向移行を実装する。

現行はNode.js 24以上・ES Modules・SQLite・Web UI・Web Push、Windowsの.NET管理画面。Web UI資産の再利用が可能なCapacitor等と、Flutter／React Native等による再構築を比較してから選ぶ。まだいずれも採用決定していない。比較ではローカルHTTP接続制約、QRスキャン、パスキーのRP・関連ドメイン、セッション、APNs/FCM、バックグラウンド復帰、オフライン表示、ストア要件と保守負担を実機で検証する。WebViewに既存サイトを表示するだけでこれらが対応済みになるとは扱わない。

## 共通IDと通信（今回実装）

`family_config.household_id` にランダムUUIDを永続化する追加マイグレーションを起動時に行う。既存の整数メンバーIDは保持し、共通のメンバー識別子は `(householdId, memberId)` とする。家庭IDをURL・家族用リンク・パスワード・購入アカウントから導出しない。再起動・パスワード変更・同一DBの移設で維持する。明示的な「全データのリセット」は新しい家庭なのでIDも再生成する。IDは公開しても権限を与えない識別子で、認証トークンとして使わない。

家族認証後の `GET /api/connection` は次を返す。既存の公開リンク保護も通る必要がある。メンバー認証や管理権限を与えるAPIではない。

```json
{
  "product": "bathjun",
  "apiVersion": 1,
  "householdId": "UUID",
  "mode": "windows-server",
  "capabilities": ["household-id", "member-api", "web-push"]
}
```

`apiVersion` は製品バージョンとは独立。`mode` は既存Windows型の常時サーバー方式を示す（開発時にLinux/macOSで起動しても同じ方式）。`capabilities` は実装済みの機能だけを列挙し、管理・移行・ネイティブ通知など未実装の能力を宣言しない。アイテム等の家庭別有効/無効は従来のstateの設定で判断する。

`public/transport.js` はDOMから独立した `request(path, data)` と `discover()` を提供する。既存Web画面は同一オリジンのCookieと家族用リンク保護を維持し、CORSや管理APIを新設しない。15秒のタイムアウト、HTTPエラー、JSON以外のゲートウェイ応答を扱う。確定操作は自動再送しない。ログイン失効時の画面復帰・古い応答の破棄は画面側の責務として残す。

接続確認はメンバーログインが有効な初期化時と、新しいログイン・登録の成功時に行う。旧v2サーバーでは未知のURLにもログイン前は401を返すため、認証後の404だけを従来接続として扱う。この場合家庭IDは不明（null）であり、移行や家庭同一性の証明には利用できない。401・通信障害・未知のAPI版を旧版と誤認しない。ネイティブで別ホストへつなぐ際の認証、QRの解析・安全な保存、通信方式の選択、常駐同期は次段階。

QRは今あるWindowsの家族用HTTPSリンクを引き続き有効とする。新しいQRには形式版、家庭ID、接続方式、接続先、短期の参加資格を含める方向で設計し、読み取り後の接続確認と家庭ID照合を必須にする。管理権限や復旧鍵を家族参加用QRに入れない。短期資格と既存リンクの互換対応は未実装。

## UI（今回実装）

画面下端の入口は「ホーム」「スタンプ」「持ち物」「設定」の4つ。画面端のsafe areaとスクロール下端の余白を確保する。認証前は表示しない。

| 入口 | 内容 |
| --- | --- |
| ホーム | 自分の予定、次に押す操作、家族のスケジュールを中心にする。希望入力・予約・変更・報告は既存の状態判定に従う |
| スタンプ | 「スタンプカード」「入浴の報告」を切り替える |
| 持ち物 | 「持ち物」「プレゼントボックス」「配布履歴」を切り替える。未受取件数も表示 |
| 設定 | 通知、自動予約、ヘルプ、プロフィールとログインへの入口 |
| 右上の自分のアイコン | 「プロフィールとログインの設定」へ直接進む。アイコン編集、パスキー確認・削除、ログアウト |

「プレゼントボックス」「持ち物」「スタンプカード」の具体的名称は維持する。「特典」への一括改名はしない。ホームの既存の状態別操作は維持し、使える場面だけ所持アイテムを控えめに出す既存機能を重複実装しない。細かな設定の折り畳みは、未保存入力の保持とともに今後検討する。

取得済みstateでタブを先に切り替え、最新データを更新する。入浴報告一覧は取得を待って表示する。確定・受取等は従来どおり処理側で再検証する。今回の変更を外部同期方式の実装やオフライン確定とは扱わない。

## ダークモード（今回実装）

クライアントの「設定 → 表示 → テーマ」で「端末に合わせる／ライト／ダーク」を選択する。初期は端末に合わせる。`bathjun.appearance` を同一オリジンのlocalStorageへ保存する端末ごとの表示設定で、家庭・メンバーの設定や移行用データには含めない。ログアウト・別メンバーへの切り替えでも同じ端末の設定を維持する。

`public/theme.js` をCSSより前に読み込み、最初の画面描画前にテーマとブラウザーのテーマ色を適用する。「端末に合わせる」ではOSの変更にも追従し、明示的に選んだライト/ダークはOS変更の影響を受けない。同じ接続先の別タブにも反映する。保存領域が使えない場合は、そのページでの変更を適用し、次回読み込みは端末設定を使う。未知の保存値は端末に合わせる設定として扱う。

色は画面・文字・境界線・警告・フォーカス等の役割ごとのCSS変数で指定する。ライト側の既存色はフォールバックとして保持する。予約/希望のメンバー色は現在のテーマ背景に混ぜ、表示切り替え時に再計算する。本人が選んだアイコンの色や配布イラスト、添付画像は元の色を保持し、単色の入浴スタンプは暗い背景でも読めるよう明るさを調整する。ダイアログ表示中や未保存フォームの入力中でも、画面を作り直さずに切り替える。

アプリ内説明書も同じテーマを利用する。公開用説明書の生成物には表示設定だけを扱う `theme.js` を明示的に同梱し、家族データやログイン情報を読み込まない。異なるオリジンの公開説明書には、アプリ内で選んだ設定を送信しない。

対象は現行のWebクライアントとWebApp。Windowsのネイティブ管理画面・ダッシュボードの配色変更は含まない。将来のiOS/AndroidアプリでのOS設定連携・ステータスバー・起動画面はネイティブ実装時に確認する。既存PWA manifestの起動画面背景は固定値なので、OSが表示する起動画面の色が必ず一致するとは扱わない。

## 同期方式と実行主体（未決定）

P2Pも候補だが、iPhoneの常時待受を必須にしない。iOSサイレントプッシュは配信・実行時刻が保証されないため、管理者iPhoneの応答を予約確定・抽選・自動予約の必要条件にしない。

Windows構成では引き続き常時サーバーが確定・抽選・自動希望確定・通知を実行する。スマホ中心構成では、最小限の外部調停で条件付き更新と時刻判定を行う案、要求時に遅延評価する案、予約実行ジョブを置く案を比較する。端末だけで作った予定は確認待ちとし、共有の確定結果と区別する。誰も開いていない時の通知や自動確定の期限を決めた上で、唯一の実行主体・サーバー時刻・競合制御・冪等キーを設計する。P2Pだけで期限保証できるとは扱わない。

無料枠評価は家庭数、人数、1日の操作数、前景/背景接続時間、スナップショットと差分のサイズ、履歴保持期間を仮定し、保存GB、転送GB、読み書き回数、関数実行数・CPU時間、接続/メッセージ数、スケジュール実行、通知、復旧用保管を数える。例えば5秒ポーリングを1時間×4人で続けると1家庭で2,880リクエスト/日、30日で86,400回になる。state取得が内部の自動処理も進める現行APIを外部サービスへそのまま移植しない。購読・差分・前景復帰時取得を候補とし、実装した試験で遅延と実測費用を計測してから事業者と価格を確定する。

## 認証・管理・通知・復旧（設計対象）

Windowsの管理操作は現在、認証されたローカルIPC専用。新しい管理APIを作る際は管理者資格と家庭ID、権限世代を処理側で検証する。画面を非表示にするだけでは認可にならない。購入権利と家庭管理権限も区別する。

端末紛失に備え、暗号化バックアップ、独立した復旧鍵または認証経路、管理者の再指定、紛失端末の資格失効、複数管理端末の競合を設計する。管理者端末内だけに唯一の鍵とデータを置かない。復旧の操作経路・保管主体とコスト・管理権限の引き継ぎが検証できるまではスマホ中心構成を完成としない。

セッション・家族用リンクは接続先依存として移行後再発行する。パスキーはRP ID、origin、アプリの関連ドメイン、秘密鍵を端末が保持する制約を確認する。移行用データに秘密鍵・ログインセッションを入れない。移行前にメンバーの再認証・同一メンバーへの再紐付け経路を確保し、家族を最初から登録し直させない方針で設計する。

WebAppはService Worker＋Web Push/VAPID、ネイティブはAPNs/FCM等の端末登録が必要。ActivityKit用の開始・更新トークンも通常の通知登録とは区別する。通知設定の希望は引き継ぐが、購読endpoint・端末トークン・配送キュー・VAPID/APNs/FCM鍵はそのまま移さない。移行時は旧配送を止め、新接続先で端末ごとに再登録し、予約revision等のイベント識別子で二重通知を避ける。実際の配送時刻は保証しない。
