# v2.1.0向けの実装・不具合調査（2026-11-05）

作業開始は04:25:44 UTC（日本時間13:25:44）。作業枠の終了予定は05:55:44 UTC（日本時間14:55:44）、90分です。公開済みv2.0.0-beta2のタグ・Release・配布物は変更しません。実際の家族のDB・バックアップを使用せず、一時DBと合成メンバーで確認しています。

## 依頼された動作

- 本人の画面からの完了報告はサーバー管理画面の共通設定とし、初期ではオフ。ダッシュボードからの報告と過去の完了記録を維持します。
- 有効な報告方法の期限を過ぎ、予約が属する日の受付終了までにホームを開いた場合、未報告の再予約を確認します。同じ予約には一度だけ自動表示し、後から手動でも開けます。
- 再予約の保存前・保存失敗時には元の枠を保持し、保存成功後だけ置き換えます。送信結果が届かなかった場合の再送でアイテムを二重消費しません。
- 初期オンの通知は、事前希望の確定失敗・入浴前・完了報告のお願い・つつくの4種類。既存の個別設定は維持します。

## 再現して修正した問題

| 問題 | 修正・確認 |
| --- | --- |
| 通信中の日付変更・予約後更新が取りこぼされ、ログアウト前の応答も残る | 強制更新を待ち合わせ、対象日・ログインが変わった応答を破棄。遅延応答で3ケースを再現・確認 |
| 固定順で、前日に入力した希望の確定がアクセスまたは希望開始まで遅れる | 日付が変わる時刻に固定順を用意し、順番に希望を確認。アクセスなしの確定と成功通知を確認し、抽選モードの手動抽選は維持 |
| 日付を切り替えただけで「予約する番」の通知が出る | 更新前の日付と比較。ブラウザーで前日への切り替えを確認 |
| 長さの選択肢が多い設定で、使用アイテムを変えると選択中の長さが戻る。時間変更不可も外れる | プルダウンとチェック状態を引き継ぎ、180分・備考・ガードを保存まで確認 |
| 公開経路などからHTMLのエラー応答が来るとJSON解析エラーになる | 接続を確認して再試行できる日本語の案内に変更。保存済みなのに502が返るケースも確認 |
| 旧様子見設定の保存失敗時に曜日設定だけ書き換わる | 同じセーブポイントで更新し、DBエラー時に両方取り消す |
| 完了報告の期限を変更・再延長すると通知が重複する。送信中のキュー再作成でも起きる | 予約revisionと通知先のハッシュで成功送信を記録。再登録・再起動後も同じ通知を繰り返さない |
| 複数端末への通知中にログアウト・通知解除・別人への端末切り替えをしても残りの送信が続く | 全5系統で送信直前にジョブと現在の通知登録を再取得。各4種類の解除操作で確認 |
| 入浴前通知の送信中に「何分前」を変えると同じ開始時刻への通知が重複する | 開始時刻単位で送信済みにする。実際の予約開始時刻を変更した場合は新しい通知を保持 |
| 別端末で曜日設定を保存した直後、編集中の別曜日を保存すると他曜日が元に戻る | 選択した曜日だけをサーバーで更新。ルール変更前の他曜日も保持して一つずつ修正可能 |
| 抽選確率UPの保存後に応答だけ失われると再試行で2枚消費する | アイテム説明画面の1操作に同じrequestIdを保持。意図的な別の使用とは区別 |
| サーバーが応答しないと読み込み・操作が長時間止まる | 本文読み込みを含む15秒の通信期限を設定し、再試行を案内 |
| ログイン切れの後、別メンバーで入ると前のパスキー一覧が表示に残る | 認証切れでもパスキー一覧・通知表示などをまとめて破棄。仮想認証器で登録・別人のログイン・パスキー再ログインまで確認 |
| ログイン・初回登録のメンバーIDに不正な型を送ると500になる | IDの型・範囲を先に検証し400で拒否。正常な数値文字列の互換性は保持 |

## 確認方法

- `npm test`：API・ドメイン239件が全件成功。通知解除・通信中の変更・不正入力の回帰テストを含みます。期限の直前直後・翌朝・受付終了・別人による操作・設定の保持・再送を含みます。
- `npm run test:browser`：Chromium、390×844、13ケース。再予約・入力内容の保持・日付変更・認証切れ・HTMLエラー・通信中の操作・翌朝の再予約。実機iPhoneではありません。
- `npm run test:sequences`：再現可能なseedで日付を進め、複数メンバーの予約・希望・様子見・取り消し・完了・アイテム・設定変更を混在。10 seed×1,200操作と、時間設定の変更・1曜日だけの保存も含めた8 seed×2,000操作を実行しました。これらで計106件の完了記録と27件の再予約の成立を含めて確認しました。各操作後に確定予約の実時刻での非重複、残高と台帳の一致、外部キー整合性、予期しない500の有無を確認します。
- Windows管理画面のチェックに、本人の完了報告の初期オフ・期限欄の有効切り替え・保存JSONを追加しました。[最初のCI](https://github.com/Slfinside/bathjun/actions/runs/41971777354)でWindows・インストーラ版・ZIP版のビルドと内容検証まで成功しました。追加修正後にも再確認します。

## 履歴が増えた場合の確認

合成した5人×5年分の予約9,125件・完了記録9,125件で、state取得の初回は約81ms、以後20回の中央値は約13ms、最大は約16msでした。返却JSONは約64KBです。このクラウド内のローカルHTTPでの測定であり、Windows端末やiPhoneの通信速度を示す数値ではありません。DBを使い捨て、実データは使用していません。

Windowsの設定画面プレビューが、非表示タブの描画によって無地になっていたため、テスト専用の通常ウィンドウへ設定欄だけを移して描画するよう修正しました。サーバー管理画面自体のLoad処理（電源制御やIPC）は起動せず、無地ならテストを失敗させます。
