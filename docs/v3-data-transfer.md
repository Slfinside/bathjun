# 家庭データの共通移行形式と切り替え（草案）

v3.0.0向けの設計契約。Windows ⇄ bathjun Serverを同じ形式で扱う。現時点で移行エクスポート・インポート・管理権限復旧の実行機能はない。`/api/connection` に移行能力は宣言しない。SQLiteファイルコピーを異なる実装間の共通形式として扱わない。

## 識別と形式

UTF-8 JSONの論理スナップショットを、認証付き暗号化コンテナーで保管・転送する。暗号方式・鍵導出・保管先とスキーマの詳細は実装前に決定する。ファイルに含むチェックサムは完全性の補助であり、管理権限の証明にしない。

形式の外枠は次の項目を持つ。形式版はAPI版・製品版と独立する。形式版1の確定前に入出力機能を公開しない。

| 項目 | 意味 |
| --- | --- |
| format / formatVersion | `bathjun-household` / `1`（草案） |
| householdId | 起点と移行後で保持するUUID |
| transferId | 1回の移行を識別するUUID。同じIDの再取り込みは二重適用しない |
| source | 製品版、方式、データスキーマ版、権限世代authorityEpoch、最後の確定revision |
| createdAt | UTCのISO 8601。予約の日付や日本時間の区切りを変換して上書きしない |
| sections | 下表の全領域。無効機能・空データでも空領域を明示する |
| integrity | 正規化ルールに従った各領域のダイジェスト。未知の必須領域は拒否 |

メンバーは既存の整数IDを家庭IDの下で保持する。予約・希望・入浴報告のrevision、配布・受取・利用のイベントIDと冪等キー、抽選結果の順番も保持する。新端末でIDを採番し直して参照を失わない。旧サーバーが家庭IDを持たない場合は対応版への更新とID発行が先に必要。

| 領域 | 引き継ぐ内容 |
| --- | --- |
| members | 無効化済みも含む家族のID・名前・プロフィール・有効状態。資格情報は別扱い |
| settings | 家庭のルール、適用日別時間帯・抽選設定・報告設定・スタンプ設定・アイテム設定 |
| planning | 抽選結果、予約、事前希望、見送り、曜日別自動予約/様子見と処理済み状態 |
| bathing | 完了・未入浴・予約外報告、過去の予約と入浴履歴、取り直しと確認済み状態 |
| stamps | 週・日別の成否/獲得履歴、達成・抽選済み・お祝い確認済み・送付済み状態 |
| items | 持ち物残高、利用台帳、使用中効果・残回数、配布バッチ、プレゼントと受取/配布履歴 |
| preferences | 通知の希望・個人設定。配送資格・端末endpoint・端末ごとのテーマ選択を含めない |
| announcements | 家庭固有のお知らせと既読状態・添付の参照。ファイルも漏れなく保護する |

各領域は現行テーブルと列の対応表を作り、未分類のテーブルがある限りエクスポートを拒否する方式を想定する。残高だけで履歴を省略しない。自動予約・スタンプ・配布の処理済みマーカーを欠落させると再実行につながる。全件数・参照整合性・revision・予約の重複と時間範囲・アイテム台帳と残高の対応を検証し、移行前後の比較を行う。未知のフィールドを黙って捨てるアップグレードはしない。

対象外：ログインセッション、家族用リンク資格、パスキーチャレンジ/秘密鍵、端末プッシュ購読・配送キュー、ActivityKitの開始/更新トークン・活動ID、VAPID鍵、管理IPC資格、購入レシート、端末固有の公開URL/ネットワーク設定。パスキー公開鍵等を引き継げる条件はRPと新しい認証経路を検証して決める。Windows内の完全バックアップと異なる接続先へのデータ移行を分ける。

## 二重更新を防ぐ切り替え

1. 両側のAPI/機能/形式版、空き容量と家庭IDを確認し、移行元の管理権限を処理側で検証する。暗号化した復元用バックアップを保存する。
2. 移行元を保守モードにし、予約・報告・配布等の書き込み、自動処理、通知配送を止める。処理中操作の完了を待って整合したスナップショットを確定する。単に画面に警告を出すだけでは不十分。
3. 移行先の隔離領域へ読み込み、家庭IDと全領域の整合性を検証する。元データに上書きせず、失敗時には一括破棄できるようにする。
4. 新しいauthorityEpochと所有権引き継ぎを確定し、唯一の書き込み先として有効化する。旧側は取り込み完了の証明を保存して読み取り専用を続ける。切り替え中に通信が切れても、タイムアウトで旧側を自動的に書き込み可能に戻さない。
5. 家族の接続先と資格、通知登録を更新する。同じ家庭・メンバーIDに再紐付けし、古い権限世代からの操作は処理側で拒否する。接続先変更をQR等で案内する。

移行先が一度でも書き込みを受けた後は、元へ戻す場合も新しい移行として差分を含む完全スナップショットを戻す。双方向を同時に書き込み可能にしない。完全にオフラインなコピー同士の排他はUUIDだけでは保証できないため、移行チケットと管理資格の失効・外部調停等の具体方式を決定してから有効化する。

## 検証の完了条件

Windows→スマホ→Windows往復で家庭/メンバーID、家族の設定、予約/希望/抽選、区切りをまたぐ入浴履歴、スタンプ・達成・使用済みアイテム・未受取プレゼント・配布履歴を比較する。再取り込み、破損・未知版・他家庭のファイル、転送中断、二重起動、権限のない要求、管理端末の紛失を検証する。セッション再ログイン、パスキー再紐付け、通知再登録・二重配送防止も必要。これらが通る前にAPIへ移行能力を追加しない。
