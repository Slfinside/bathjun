# 入浴直前〜直後のライブアクティビティ（v3向け要件・設計案）

2026-11-12追加。利用者から「入浴直前から直後までライブアクティビティも欲しい」と依頼された機能。iOS版ふろじゅんの要件に含める。現時点は設計段階で、Swift・Xcodeプロジェクト、ActivityKitの表示、開始予約、APNs登録・送信は未実装。MacBookでのネイティブ開発時に実装・実機検証する。WebAppに対応済みとは扱わず、APIのcapabilitiesにもまだ宣言しない。

## 表示と操作

本人の確定予約を対象に、ロック画面と対応機種のDynamic Islandに表示する。事前希望・時刻未定の希望を確定予約として表示しない。直前・直後の具体的な分数は未確定。開始10分前〜予定終了10分後を試す案とし、採用決定や保証値として扱わない。

| 状態 | 表示・操作の案 |
| --- | --- |
| 開始直前 | 「おふろまであとn分」、予約の開始〜終了予定 |
| 予約時間内・完了未報告 | 「終了予定まであとn分」、予約時間。時刻だけで実際の入浴開始を確定しない |
| 予定終了直後・完了未報告 | 「予定時間が終了しました」、入浴報告への入口。「入浴済み」とは表示しない |
| 完了報告が受理された | 「完了を報告しました」を短時間表示して終了。早上がりの場合も反映する |
| 未入浴・キャンセル・予約の置き換え | 古い予約の表示と開始予約を取り消し、新しい確定予約があればその時刻に合わせる |
| 更新を確認できない | 最終取得時点の予定であることを示し、未確認の報告成功や最新状態を断定しない |

タップで本人の予約・入浴報告画面へ進む。初期実装はアプリへ開く導線を用意し、Live Activity上の直接報告はApp Intents等で既存の認証・報告条件を満たせるか確認してから追加する。直接報告を行う場合も処理側の成功応答まで完了表示にしない。通信失敗時にスタンプを付与したり、報告済みとして活動を閉じたりしない。

報告操作には、既存の `clientReportEnabled`、本人認証、予約revision、その日分の報告期限を適用する。表示期間は報告受付期間とは別であり、ライブアクティビティの終了時刻を受付期限にしない。完了報告が無効な家庭では、その操作を提供しない。既存の抽選・予約・スタンプ・取り直しの条件は変えない。

ロック画面へ出すのは本人の予定と最小限の状態。家族全員の氏名・予定、備考、管理情報、認証資格は載せない。ライト/ダーク、文字サイズ、VoiceOver、Dynamic Islandの各表示形態を確認する。Androidの同等表示は別のOS機能として設計し、ActivityKitを共通APIとして扱わない。

## 実装の分担

Appleの[ActivityKitの表示・開始・開始予約の資料](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)と[プッシュによる開始・更新・終了の資料](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications)を確認した。以下は、それらを踏まえたふろじゅん側の設計案。

- iOSの表示部分はActivityKitとWidgetKit/SwiftUIの拡張が必要。アプリ本体の採用技術とは分けて検討する。Capacitor・Flutter・React Native等を選ぶ場合も、この拡張とネイティブ連携の成立を選定条件に加える。
- 予約を取得済みの端末では、対応OSの日時指定開始APIを評価する。APIの利用可否・開始時のアラート・更新/取り消し・件数制限はMac上のSDKと実機で確認する。アプリ内のタイマーやサイレントプッシュで、直前に必ずアプリが起動するという前提を置かない。
- 別端末での予約変更・キャンセル・完了報告を閉じたアプリにも反映するには、ActivityKit用のAPNs更新等を設計する。通常のWeb Pushやサイレントプッシュを、そのままActivityKitの配送として流用しない。表示拡張から既存のstateをポーリングする構成にしない。
- 残り時間は開始/終了の絶対時刻を渡し、OSのタイマー表示で進める。秒・分ごとのプッシュやAPI取得を必要条件にしない。通信は予約内容・報告結果等の変更時と、必要な開始・終了に絞る。
- `staleDate` と終了・消去方針を定め、古い予定を最新と誤認させない。OSによる配信抑制・表示許可・表示時間上限・利用者による削除を扱う。Live Activityが出ない場合も、通常のアプリ・通知から利用できる。時間通りの表示や配送を予約確定の条件にしない。

利用者によるLive Activitiesの許可と、ふろじゅんの表示設定を確認する。通常の入浴前通知をオフにしただけで、この表示もオフになるという結合はしない。表示する期間・既存通知との重複・開始アラートの扱いは実機を見て調整する。未実装の設定項目を現行Web画面には追加しない。

## Windows構成とスマホ中心構成

Windows利用家庭も無料のふろじゅん側の機能として設計し、bathjun Server購入を条件にしない。Windows構成では既存サーバーが予約・報告の正しい状態を持ち、スマホ中心構成では採用する共通の確定処理が持つ。管理者のiPhoneが起動していることを必要条件にしない。

APNsの送信資格を各家庭のWindows PCへ埋め込む構成にはしない。運営の最小限の仲介処理を使う案等を、未決定の同期方式と合わせて評価する。仲介を設ける場合も、家庭・本人・端末・予約への配送権限を処理側で検証し、他家庭への任意送信を防ぐ。LANだけの接続やサーバー停止・外部通信不可のときは、取得済みの予定と最新の確認済み結果を区別する。端末内の開始予約だけで、他端末からの変更まで確実に反映できるとは扱わない。

費用見積もりには通常の通知とは別に、端末登録、開始/更新/終了の配送、ジョブ、再試行、読み書き、保存、転送を加える。件数は概ね「確定予約数×登録端末数×（開始・終了＋変更回数）」を基にし、冪等処理で重複配送を抑える。毎秒更新をクラウド処理回数へ変換しない。事業者・無料枠・契約の採用はまだ決定しない。

## 識別・移行・復旧

配送先は家庭ID、本人のメンバーID、端末登録、予約日と現在のrevisionで検証する。予約編集時は旧revisionの保留中ジョブを無効化し、新しい予約に追従させる。古い終了/取消通知が新しい予約の活動を閉じないよう、活動との対応と更新順序を管理する。家族用リンク・ログイン資格を表示payloadに載せない。

ActivityKitの開始用・更新用トークンと活動IDは、通常の通知登録とも家庭の移行データとも分ける。トークン変更、失効、ログアウト、メンバー変更、紛失端末の解除、接続先移行を扱い、新接続先で再登録する。旧接続先の配送を止め、残った表示・開始予約も整理する。二重起動・再試行で同じ本人の同じ予約を重複表示しない。

## Macでの検証項目

- 直前・開始・予定終了・早上がり報告・未入浴・キャンセル・順番抜かし・時間変更・日付境界と区切りをまたぐ予約。
- アプリ前景/背景/終了状態、予定取得後に別端末で編集、ネットワーク断・復帰、古い更新の遅着、APNs失敗・重複・トークン更新。
- 開始予約の対応/非対応OS、Live Activities許可の無効化、本人による削除、OS制限、端末時計変更。
- ロック画面・Dynamic Island・文字拡大・ライト/ダークと、本人情報の出し過ぎがないこと。
- 報告期限・処理側の本人認証・冪等性と、報告失敗時に完了やスタンプ成功を表示しないこと。
- Windows利用家庭に管理アプリ購入を求めないこと、管理者端末を閉じても必要な処理が成立すること、接続先移行・管理復旧・ログアウト後の表示終了。

ブラウザー上の疑似表示をActivityKitの実機検証の代わりにしない。今回は要件・設計文書だけを追加し、公開・課金・通知送信資格の作成やクラウド契約は行っていない。
