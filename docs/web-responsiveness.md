# Web版のレスポンス改善（開発中）

目的は、低スペックの常設PCで配信しながら、起動とタップ後の待ちを減らすことです。アプリ版と同等の性能を保証するものではありません。ブラウザーの起動、画面の描画、予約確定に必要な通信は分けて評価します。

## 今回変更したこと

- ログイン済みの起動を、家族認証状態→メンバー→予約情報の3回の直列通信から、`GET /api/bootstrap`の1回にまとめました。家族認証前にはメンバーを返さず、個別ログイン前には予約や本人の持ち物を返しません。期限切れは対応するログイン画面へ戻します。
- 起動時に必要な2つの小さいモジュールをHTMLから並列に読み込みます。最初の画面が出た後に、設定・ヘルプ等で共用する画面モジュールを先読みします。先読みが失敗した場合も、その後の操作で再試行できます。
- ホーム・設定・持ち物などは、最後に受信した情報で先に表示し、その後に最新状態を確認します。通信を待つ間も操作でき、入力中の通知設定を後からの応答で上書きしません。
- 入浴報告の一覧は専用情報が必要なため、取得を待ちます。予約・報告・アイテム消費などの確定は引き続きサーバー応答を待ちます。表示を先に切り替えただけで予約成功にはしません。
- APIは`no-store`を維持し、本人のデータを端末の永続ストレージへ追加保存しません。既存のAPIも残します。サーバーはNode.js＋SQLiteのままで、依存パッケージや新たな定期通信は増やしません。

初期画面の圧縮サイズ上限は維持します。画面モジュールの先読みはBrotliで約1.4KBです。最初の画面と同時にすべての補助画面・説明書を読む方式にはしません。

## 計測結果

2026-11-17に、変更前`c653d0e`と今回の変更を比較しました。架空の5人分の一時DBを使い、各条件を3回計測した中央値です。

- Chromium、390×844の画面、タッチ操作相当。
- 通信遅延150ms、受信約10Mbps、ブラウザーCPUを4倍遅くする設定。
- 配信元はクラウド上のNode.jsです。実際の低スペックPCのCPUを再現した測定ではありません。
- 初回表示は新しいブラウザーコンテキスト、再読み込みは同じコンテキストです。見える状態になった後、2回の描画タイミングを待って計測します。文字フォントの取得完了時刻も別に記録します。
- 画面切り替えはタップから対象画面の表示までです。先に表示した内容が最新の受信データかどうかは、この時間には含めません。

| 操作 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 初回表示 | 1,657ms | 1,144ms |
| 再読み込み | 1,525ms | 738ms |
| 設定 | 921ms | 209ms |
| 持ち物 | 290ms | 134ms |
| ヘルプ | 345ms | 170ms |
| 入浴の報告 | 874ms | 294ms |
| ホーム | 291ms | 156ms |
| 予約入力フォームを開く | 159ms | 198ms |

予約フォームの表示は今回改善しておらず、この試験ではむしろ遅い値でした。3回だけの簡易測定なので細かい差を断定できませんが、起動とメニューの通信待ちを減らす変更で、すべての引っ掛かりが解消したとは扱いません。

初回に読み込む本文・フォント等は両方とも約0.30MBでした。大幅なデータ量削減による差ではなく、通信の直列待ちと、通信後まで画面を表示しない処理を減らした結果です。

## 再計測

Chrome/ChromiumとNode.js 24以降があるソース環境で実行します。

```sh
BATHJUN_AUDIT_LATENCY=150 BATHJUN_AUDIT_NAME=current npm run bench:client
```

結果の保存先はログに表示します。`BATHJUN_AUDIT_OUTPUT`で保存フォルダー、`BATHJUN_BROWSER_PATH`でChromiumの実行ファイル、`BATHJUN_AUDIT_ROOT`で比較したいソースの別チェックアウトを指定できます。遅延を省略すると0・150・300msを各3回実行します。`readyMs`は画面表示、`visualReadyMs`はその後にフォントも読み終えた時刻です。JSONにはAPIの回数・時刻、転送量、50ms以上のブラウザー処理、試験サーバーのAPI処理時間も残します。実際のDBや家族用リンクは使いません。

## 残る確認と次の候補

- iPhoneのSafari／ホーム画面アプリでの起動とスクロール、実際のTailscale経由の待ち時間を確認する。
- 全体を再描画する更新を減らし、入力やスクロール中の更新で引っ掛からないようにする。
- 画面用のファイルを端末へ保持して、再起動時の再取得・更新確認を減らす。ただし更新時のファイルの組み合わせと、家族用リンクのリセット・認証の扱いを設計してから導入する。
- 履歴が長くなった試験データでサーバー側の負荷を計測する。履歴の再計算や一覧の返却量に上限・差分が必要かを判断する。

これらは今回すべて実装したという意味ではありません。アプリ版でも共有するAPIを軽くしながら、Web版単体の応答を改善するための共通の記録です。
